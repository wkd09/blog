vLLM은 LLM 추론을 효율적으로 서빙하기 위한 오픈소스 엔진이다.

LLM을 실제 서비스에 붙이면 단순히 모델을 한 번 실행하는 것보다 더 많은 문제가 생긴다. 여러 사용자의 요청을 동시에 처리해야 하고, GPU 메모리를 효율적으로 써야 하며, 응답 지연 시간도 관리해야 한다.

vLLM은 이 문제를 **continuous batching**과 **PagedAttention** 같은 방식으로 풀어낸다.

![vLLM의 scheduler, KV cache manager, worker 구조]({{ '/assets/images/blog/vllm.png' | relative_url }})

*vLLM은 scheduler가 요청을 관리하고, KV cache manager가 block table을 통해 cache block을 할당하며, worker들이 model shard와 cache engine을 사용해 추론을 수행한다.*

![vLLM 원문 Figure: KV cache memory management]({{ '/assets/images/blog/vllm-paper-figure.png' | relative_url }})

*원 논문 Figure 3은 기존 시스템에서 생기는 reserved, internal fragmentation, external fragmentation을 보여준다.*

## 왜 LLM Serving이 어려운가

LLM 추론은 일반적인 딥러닝 inference보다 까다롭다.

첫 번째 이유는 autoregressive generation이다. 모델은 한 번에 전체 답변을 만드는 것이 아니라 다음 토큰을 하나씩 생성한다. 즉, 요청 하나가 여러 번의 forward pass를 필요로 한다.

두 번째 이유는 요청마다 길이가 다르다는 점이다. 어떤 사용자는 짧은 질문을 하고, 어떤 사용자는 긴 문맥을 입력한다. 출력 길이도 매번 다르다.

세 번째 이유는 KV cache 메모리다. Transformer decoder는 이전 토큰의 key, value를 cache해 다음 토큰 생성에 재사용한다. 이 cache는 속도를 높여주지만, 요청이 많아질수록 GPU 메모리를 크게 차지한다.

## Batch Inference의 한계

일반적인 batch inference는 여러 요청을 묶어서 한 번에 처리한다. GPU 사용률을 높이는 데 유리하지만, LLM serving에서는 문제가 있다.

요청마다 생성 길이가 다르기 때문에 먼저 끝난 요청이 있어도 batch 전체가 끝날 때까지 비효율이 생길 수 있다. 또 새로운 요청이 들어와도 기존 batch가 끝나기 전까지 기다려야 한다.

서비스 입장에서는 처리량은 높이고 싶지만, 사용자의 응답 지연 시간도 낮춰야 한다. 이 둘을 동시에 챙기는 것이 어렵다.

## Continuous Batching

Continuous batching은 batch를 고정된 묶음으로 보지 않는다.

요청이 끝나면 그 자리에 새로운 요청을 넣고, 실행 중인 요청들과 함께 계속 batch를 재구성한다. 즉, GPU가 쉬는 시간을 줄이고, 새 요청이 오래 대기하지 않도록 만든다.

이 방식은 LLM처럼 토큰을 반복 생성하는 workload에 잘 맞는다.

예를 들어 A 요청은 30토큰만 생성하고, B 요청은 300토큰을 생성한다고 가정해보자. 고정 batch에서는 A가 먼저 끝나도 B가 끝날 때까지 GPU 자리가 비효율적으로 남을 수 있다. Continuous batching은 A가 끝난 자리에 C 요청을 넣어 GPU를 계속 채운다.

이 차이는 동시 요청이 많아질수록 커진다. 단일 요청 latency만 보면 차이가 작아 보여도, 서비스 전체 throughput에서는 큰 차이를 만든다.

## PagedAttention

PagedAttention은 KV cache 메모리를 더 효율적으로 관리하기 위한 vLLM의 핵심 아이디어다.

운영체제의 virtual memory와 비슷하게, KV cache를 연속된 큰 메모리 덩어리로 관리하지 않고 block 단위로 나누어 관리한다. 요청마다 필요한 만큼 block을 할당하고, 불필요한 낭비를 줄인다.

![PagedAttention에서 query token이 block 단위 KV cache를 참조하는 예시]({{ '/assets/images/blog/vllm01.png' | relative_url }})

*PagedAttention은 token의 key/value를 고정 크기 block에 나누어 저장하고, 요청별 block table을 통해 필요한 block만 참조한다.*

이 방식은 다음 장점이 있다.

- GPU 메모리 fragmentation 감소
- 더 많은 동시 요청 처리
- 긴 context를 다룰 때 메모리 효율 개선
- serving 처리량 향상

LLM serving에서는 KV cache가 병목이 되는 경우가 많기 때문에, 이 부분을 효율적으로 관리하는 것이 중요하다.

KV cache는 요청 길이가 길수록 커지고, batch 안의 요청 수가 많을수록 더 많이 필요하다. 모델 weight는 한 번 올라가면 고정 비용에 가깝지만, KV cache는 traffic과 context length에 따라 계속 변하는 동적 비용이다.

그래서 serving 최적화에서는 모델 weight 크기뿐 아니라 `max_model_len`, 동시 요청 수, beam search 여부, sampling 설정까지 함께 봐야 한다.

## OpenAI 호환 API

vLLM은 OpenAI API와 호환되는 서버 형태로도 실행할 수 있다.

기존 애플리케이션이 OpenAI Chat Completions API 형태를 사용하고 있다면, endpoint만 바꾸어 자체 모델 serving으로 연결하기 쉽다.

이 점은 실험용 모델을 빠르게 서비스에 붙이거나, 내부 모델을 OpenAI 호환 인터페이스로 제공할 때 유용하다.

예시 형태는 다음과 같다.

```bash
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --host 0.0.0.0 \
  --port 8000
```

이후 client에서는 OpenAI SDK의 base URL만 vLLM 서버 주소로 바꿔 호출할 수 있다.

## 운영에서 자주 보는 병목

vLLM을 운영할 때 병목은 보통 세 가지로 나타난다.

첫째, GPU memory가 부족해 동시 요청 수를 늘리지 못하는 경우다. 이때는 더 작은 모델, 양자화, context length 제한, tensor parallelism을 검토한다.

둘째, first token latency가 높은 경우다. prompt prefill 단계가 오래 걸리면 사용자는 응답이 시작되기 전부터 느리다고 느낀다. 긴 prompt가 많다면 prompt 길이를 줄이거나 prefix cache 같은 기능을 검토할 수 있다.

셋째, decode throughput이 부족한 경우다. 이미 응답은 시작됐지만 token 생성 속도가 느리면 전체 completion 시간이 길어진다. 이때는 batch 설정, GPU 사용률, sampling 옵션을 함께 봐야 한다.

## 성능을 볼 때 확인할 것

vLLM을 사용할 때는 단순히 모델이 실행되는지만 보면 부족하다.

다음 지표를 함께 확인해야 한다.

- Throughput: 초당 처리 가능한 요청 수 또는 토큰 수
- Latency: 첫 토큰 지연 시간과 전체 응답 시간
- GPU memory usage: KV cache와 모델 weight가 차지하는 메모리
- 동시 요청 처리 성능
- context length 증가에 따른 성능 변화

특히 서비스에서는 평균 latency보다 p95, p99 latency가 중요할 수 있다. 일부 요청이 심하게 느려지면 사용자 경험이 바로 나빠진다.

## 내가 이해한 핵심

vLLM은 LLM을 실제 서비스 환경에서 효율적으로 서빙하기 위한 도구다.

핵심은 다음과 같다.

- LLM 추론은 autoregressive generation과 KV cache 때문에 serving이 어렵다.
- continuous batching은 GPU 사용률과 요청 대기 시간을 개선한다.
- PagedAttention은 KV cache 메모리를 block 단위로 관리해 낭비를 줄인다.
- OpenAI 호환 API를 사용하면 기존 애플리케이션과 연동하기 쉽다.

모델 성능만큼 중요한 것이 serving 성능이다. 실제 서비스를 만들 때는 모델의 정확도뿐 아니라 처리량, 지연 시간, 메모리 사용량까지 함께 봐야 한다.
