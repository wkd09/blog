# GQA(Grouped-Query Attention) 이해하기: MHA와 MQA 사이의 균형점

이 글은 논문 [GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints](https://arxiv.org/abs/2305.13245)를 바탕으로 MHA, MQA, GQA의 차이를 정리한 글이다.

핵심 관심사는 하나다.

> LLM이 긴 context를 처리하고 긴 답변을 생성할 때, 왜 `KV cache`가 커지고, GQA는 이 문제를 어떻게 줄이는가?

논문에서 확인 가능한 내용과 개인적인 해석은 구분해서 적었다. 논문에서 직접 확인되는 실험 결과는 "논문 기준"으로 표시하고, 이해를 돕기 위한 문장 예시는 "해석용 예시"로 표시한다.

## 1. 핵심 요약

- **MHA**는 Query head마다 별도의 Key/Value head를 둔다. 표현력은 좋지만 KV cache가 크다.
- **MQA**는 여러 Query head가 하나의 Key/Value head를 공유한다. KV cache가 작고 decoding이 빨라질 수 있지만 품질 손실이 생길 수 있다.
- **GQA**는 Query head를 여러 group으로 나누고, 각 group이 하나의 Key/Value head를 공유한다.
- 논문에서는 GQA를 **MQA와 MHA 사이를 일반화한 구조**로 설명한다.
- 논문 실험에서 uptrained GQA는 MQA에 가까운 속도와 MHA에 가까운 품질을 목표로 하며, 실제로 T5-XXL 실험에서 좋은 trade-off를 보였다.

```text
MHA: KV head 많음  -> cache 큼, 표현력 좋음
MQA: KV head 1개   -> cache 작음, 빠름, 품질 손실 가능
GQA: KV head G개   -> 둘 사이의 절충점
```

## 2. 배경: 왜 KV cache가 문제가 되는가

LLM의 autoregressive decoding은 토큰을 하나씩 생성한다.

```text
입력 문장 -> 다음 토큰 1개 생성
입력 문장 + 생성 토큰 1개 -> 다음 토큰 1개 생성
입력 문장 + 생성 토큰 2개 -> 다음 토큰 1개 생성
...
```

이때 매 step마다 이전 모든 토큰의 Key와 Value를 다시 계산하면 너무 비싸다. 그래서 Transformer decoder는 각 layer에서 이전 토큰들의 `K`, `V`를 저장해두고 다음 step에서 재사용한다. 이것이 **KV cache**다.

문제는 context length가 길어질수록 저장해야 할 K/V가 계속 커진다는 점이다.

```text
긴 prompt
  -> 많은 token
  -> 각 layer마다 K/V 저장
  -> KV cache 증가
  -> decode step마다 읽어야 할 K/V 증가
  -> memory bandwidth 부담 증가
```

논문도 decoder inference의 병목을 설명할 때, 매 decoding step에서 decoder weight와 attention key/value를 메모리에서 불러오는 비용을 강조한다. 즉 GQA의 핵심은 단순히 attention 모양을 바꾸는 것이 아니라, **decoding 중 읽고 저장해야 하는 K/V의 양을 줄이는 것**이다.

## 3. 구조 비교: MHA, MQA, GQA

아래 그림은 논문에 나온 MHA, GQA, MQA 구조 비교다.

![MHA, GQA, MQA의 Query-Key-Value head 공유 구조]({{ '/assets/images/blog/gqa-mha-gqa-mqa.png' | relative_url }})

*논문 기준: MHA는 Query, Key, Value head 수가 같고, MQA는 모든 Query head가 하나의 Key/Value head를 공유한다. GQA는 그 중간처럼 Query head group마다 하나의 Key/Value head를 공유한다.*

## 4. MHA: Query head마다 K/V head를 따로 둔다

Multi-Head Attention에서는 여러 attention head가 서로 다른 관점에서 토큰을 본다.

- `Query`: 지금 생성하려는 토큰이 무엇을 찾고 있는지
- `Key`: 이전 토큰들이 어떤 특징을 가지고 있는지
- `Value`: 실제로 가져올 정보

MHA에서는 보통 Query head 수와 Key/Value head 수가 같다.

```text
Q1 -> K1, V1
Q2 -> K2, V2
Q3 -> K3, V3
Q4 -> K4, V4
```

각 Query head가 자기만의 K/V 공간을 사용하므로 표현력이 좋다. 예를 들어 어떤 head는 주어를 보고, 어떤 head는 시간 표현을 보고, 어떤 head는 목적어를 보는 식으로 역할이 나뉠 수 있다.

하지만 단점도 명확하다. KV cache에 저장해야 하는 K/V head 수가 많다.

```text
Query head = 32
MHA KV head = 32
```

긴 context에서 32개의 K head와 32개의 V head를 layer마다 저장하고, decode step마다 읽어야 한다. 그래서 MHA는 품질 측면에서는 강하지만 inference memory bandwidth 측면에서는 비싸다.

## 5. MQA: 모든 Query head가 하나의 K/V head를 공유한다

Multi-Query Attention은 Query head는 여러 개 유지하되, Key/Value head는 하나만 사용한다.

```text
Q1 ┐
Q2 ├──> K1, V1
Q3 │
Q4 ┘
```

이 구조에서는 Query head가 32개여도 KV head는 1개다.

```text
Query head = 32
MQA KV head = 1
```

장점은 분명하다.

- KV cache 크기가 크게 줄어든다.
- decode step에서 읽어야 할 K/V 양이 줄어든다.
- memory bandwidth 부담이 줄어 decoding speed가 좋아질 수 있다.

하지만 모든 Query head가 같은 K/V를 공유한다. 따라서 각 head가 독립적인 K/V 표현을 갖는 MHA보다 표현력이 줄어들 수 있다. 논문도 MQA가 decoder inference를 크게 빠르게 만들 수 있지만, quality degradation이 생길 수 있다고 설명한다.

쉽게 말하면, MHA는 여러 명의 전문가가 각자 다른 자료집을 들고 보는 구조에 가깝고, MQA는 여러 전문가가 하나의 공용 자료집만 보는 구조에 가깝다. 이 비유에서 "자료집"은 실제로는 Key/Value projection과 KV cache에 해당한다.

## 6. GQA: Query head를 group으로 묶어 K/V를 공유한다

Grouped-Query Attention은 MHA와 MQA의 중간 구조다.

Query head를 여러 group으로 묶고, 각 group이 하나의 Key/Value head를 공유한다.

```text
Q1, Q2 -> K1, V1
Q3, Q4 -> K2, V2
```

조금 더 크게 보면 다음과 같다.

```text
Query heads: Q1 Q2 Q3 Q4 Q5 Q6 Q7 Q8

Group 1: Q1 Q2 -> K1, V1
Group 2: Q3 Q4 -> K2, V2
Group 3: Q5 Q6 -> K3, V3
Group 4: Q7 Q8 -> K4, V4
```

논문에서는 `GQA-G`를 group 수가 `G`개인 grouped-query attention이라고 부른다.

- `GQA-1`: group이 1개이므로 모든 Query head가 하나의 K/V를 공유한다. 즉 **MQA와 같다**.
- `GQA-H`: group 수가 head 수 `H`와 같으므로 Query head마다 K/V가 있다. 즉 **MHA와 같다**.

```text
GQA-1  = MQA
GQA-H  = MHA
GQA-G  = MQA와 MHA 사이의 일반화된 구조
```

따라서 GQA는 "새로운 완전히 다른 attention"이라기보다, **KV head 수를 조절할 수 있게 만든 일반화된 attention 구조**로 이해하는 편이 정확하다.

## 7. 실제 문장 예시로 보기

해석용 예시로 다음 문장을 보자.

```text
나는 오늘 학교에서 친구와 코딩 공부를 했다
```

모델이 이 문장 다음 토큰을 생성한다고 가정하자. 여러 attention head는 서로 다른 정보에 집중할 수 있다.

```text
Head A: "나는"          -> 주어 정보
Head B: "오늘"          -> 시간 정보
Head C: "학교에서"      -> 장소 정보
Head D: "코딩 공부"     -> 행동 정보
```

MHA에서는 각 head가 자기만의 K/V를 가진다.

```text
Head A: Q_A -> K_A, V_A  # 주어를 보는 데 유리한 표현
Head B: Q_B -> K_B, V_B  # 시간을 보는 데 유리한 표현
Head C: Q_C -> K_C, V_C  # 장소를 보는 데 유리한 표현
Head D: Q_D -> K_D, V_D  # 행동을 보는 데 유리한 표현
```

MQA에서는 Query head는 여러 개지만 K/V는 하나다.

```text
Head A: Q_A ┐
Head B: Q_B ├──> K_shared, V_shared
Head C: Q_C │
Head D: Q_D ┘
```

각 Query head가 질문하는 방식은 다를 수 있지만, 참고하는 K/V 표현은 공통이다. 그래서 cache는 작아지지만, 모든 head가 같은 K/V를 공유한다는 제약이 생긴다.

GQA에서는 비슷한 역할을 하는 head끼리 group을 만든다고 볼 수 있다.

```text
Group 1: Head A, Head B -> K_group1, V_group1  # 주어/시간
Group 2: Head C, Head D -> K_group2, V_group2  # 장소/행동
```

이 예시는 이해를 돕기 위한 단순화다. 실제 모델에서 head가 정확히 "주어 전담", "장소 전담"처럼 사람이 붙인 역할로 고정되는 것은 아니다. 다만 GQA의 구조적 차이를 이해하기에는 유용하다.

## 8. KV cache 관점에서 비교하기

요청한 관계식으로 쓰면 KV cache 크기는 대략 다음 요소에 비례한다.

```text
KV cache 크기 ∝ layer 수 × sequence length × KV head 수 × head_dim × 2
```

여기서 `×2`는 Key와 Value를 모두 저장하기 때문이다.

실제 메모리 계산에서는 batch size와 dtype 크기도 들어간다.

```text
KV cache memory
≈ batch_size
  × layer 수
  × sequence length
  × KV head 수
  × head_dim
  × 2              # Key + Value
  × bytes_per_elem
```

중요한 항목은 `KV head 수`다.

```text
Query head = 32

MHA KV head = 32
GQA KV head = 8
MQA KV head = 1
```

같은 layer 수, sequence length, head_dim을 가정하면 KV head 수만큼 cache 크기와 K/V load 비용이 달라진다.

```text
MHA: 32개 KV head 저장
GQA:  8개 KV head 저장
MQA:  1개 KV head 저장
```

따라서 GQA-8은 이 단순 비교에서 MHA 대비 KV head 수를 `32 -> 8`로 줄인다. KV cache의 K/V head 차원만 보면 1/4 수준이다. 반면 MQA처럼 1개로 줄이지는 않기 때문에, MQA보다 더 많은 K/V 표현을 유지할 수 있다.

이 지점이 GQA의 핵심 trade-off다.

```text
MHA 대비:
  - KV cache 감소
  - K/V memory bandwidth 감소
  - decoding speed 개선 가능

MQA 대비:
  - KV cache는 더 큼
  - 하지만 K/V 표현을 group별로 나눌 수 있음
  - 품질 손실을 줄일 가능성
```

단, 실제 speedup은 모델 크기, sequence length, batch size, GPU/TPU 특성, inference engine의 구현에 따라 달라진다. GQA 구조를 쓴다고 항상 같은 비율로 빨라지는 것은 아니다.

## 9. 논문 핵심 기여

논문 제목은 **GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints**다. 핵심은 이미 학습된 MHA checkpoint를 MQA/GQA 구조로 바꾸고, 적은 추가 학습으로 적응시키는 방법이다.

### 9.1 기존 MHA checkpoint를 변환한다

논문은 MHA 모델을 새로 처음부터 학습하는 대신, 기존 multi-head checkpoint를 MQA 또는 GQA 구조로 변환한다.

MQA로 바꿀 때는 여러 K/V projection head를 하나로 줄여야 한다. 논문에서는 Key projection과 Value projection을 head 방향으로 **mean pooling**하는 방법을 사용한다.

![MHA checkpoint의 여러 Key projection을 mean pooling해 MQA Key projection으로 변환]({{ '/assets/images/blog/gqa-mean-pooling.png' | relative_url }})

```text
K1, K2, K3, ..., KH
        |
        | mean pooling
        v
K_MQ

V1, V2, V3, ..., VH
        |
        | mean pooling
        v
V_MQ
```

GQA에서는 전체 head를 하나로 평균내는 것이 아니라, group 안의 K/V head끼리 평균낸다.

```text
Group 1: K1, K2, K3, K4     -> mean -> K_group1
Group 2: K5, K6, K7, K8     -> mean -> K_group2
...
```

논문 기준으로는 mean pooling이 첫 번째 head를 선택하거나 random initialization을 쓰는 것보다 나은 결과를 보였다.

![K/V checkpoint 변환 방식별 성능 비교]({{ '/assets/images/blog/gqa-conversion-ablation.png' | relative_url }})

### 9.2 변환 후 uptraining을 수행한다

구조를 바꾸면 모델이 바로 원래처럼 잘 동작한다고 보장할 수 없다. 그래서 논문은 변환된 모델을 원래 pretraining recipe로 조금 더 학습시키는 **uptraining**을 수행한다.

논문에서는 원래 pretraining compute의 작은 비율을 사용한다. 대표 실험에서는 `α = 0.05`, 즉 원래 pretraining steps의 5%에 해당하는 추가 학습을 사용했다.

![Uptraining proportion에 따른 MQA/GQA 성능 변화]({{ '/assets/images/blog/gqa-uptraining-proportion.png' | relative_url }})

논문 기준으로는 MQA와 GQA 모두 5% uptraining에서 성능이 개선되며, 10%로 늘렸을 때는 추가 개선 폭이 줄어드는 경향을 보였다.

### 9.3 GQA는 MQA에 가까운 속도와 MHA에 가까운 품질을 목표로 한다

논문은 GQA가 MQA와 MHA 사이의 trade-off를 제공한다고 주장한다.

![GQA, MQA, MHA의 평균 성능과 inference time 비교]({{ '/assets/images/blog/gqa-speed-quality.png' | relative_url }})

논문 Table 1의 T5-XXL 기준 결과를 요약하면 다음과 같다.

![논문 Table 1: MHA, MQA, GQA의 inference time과 downstream task 성능]({{ '/assets/images/blog/gqa-results-table.png' | relative_url }})

```text
MHA-XXL:    inference time 1.51s, average 47.2
MQA-XXL:    inference time 0.24s, average 46.6
GQA-8-XXL:  inference time 0.28s, average 47.1
```

이 결과만 보면 GQA-8은 MQA보다 약간 느리지만 MHA보다 훨씬 빠르고, 평균 성능은 MHA-XXL에 매우 가깝다.

다만 이 숫자는 논문의 실험 설정에 묶여 있다. T5.1.1 기반, 특정 task 조합, 특정 TPU 환경, 논문이 선택한 parallelization 조건에서 측정된 결과다. 다른 모델과 serving 환경에서 그대로 같은 비율을 기대하면 안 된다.

### 9.4 group 수가 trade-off를 정한다

GQA에서 group 수가 많아질수록 MHA에 가까워진다. 그러면 KV head 수가 늘어나므로 cache와 memory bandwidth 비용도 커진다.

반대로 group 수가 적어질수록 MQA에 가까워진다. 그러면 속도와 cache 측면에서는 유리하지만 표현력은 더 줄어들 수 있다.

![GQA group 수에 따른 inference time 변화]({{ '/assets/images/blog/gqa-groups-speed.png' | relative_url }})

논문에서는 8 groups를 좋은 middle ground로 선택했다. 이것은 모든 모델에 보편적으로 정답이라는 뜻이 아니라, 해당 실험 설정에서의 선택이다.

## 10. MHA vs MQA vs GQA 표

| 항목 | MHA | MQA | GQA |
| --- | --- | --- | --- |
| 구조 | Query head마다 K/V head를 따로 둠 | 모든 Query head가 하나의 K/V head 공유 | Query head group마다 하나의 K/V head 공유 |
| Query head 수 | H | H | H |
| KV head 수 | H | 1 | G |
| KV cache 크기 | 큼 | 가장 작음 | 중간 |
| 속도 | 상대적으로 느릴 수 있음 | 빠른 편 | MQA에 가까운 속도를 목표 |
| 품질 | 표현력 좋음 | 품질 손실 가능 | MHA에 가까운 품질을 목표 |
| 특징 | 가장 일반적인 multi-head 구조 | memory bandwidth 절감이 큼 | 속도와 품질 사이의 조절 가능한 절충안 |

이를 head 수 예시로 다시 쓰면 다음과 같다.

```text
Query head = 32

MHA:
  KV head = 32
  cache 많음

MQA:
  KV head = 1
  cache 가장 적음

GQA-8:
  KV head = 8
  cache는 MHA보다 작고, MQA보다 큼
```

## 11. 한계와 주의점

GQA는 좋은 절충안이지만 만능 해결책은 아니다.

첫째, GQA가 항상 모든 모델과 모든 task에서 MHA와 동일한 품질을 보장하는 것은 아니다. 논문에서도 실험은 T5 계열 encoder-decoder 모델을 중심으로 진행했다.

둘째, group 수 선택에 따라 속도와 품질 trade-off가 달라진다. group 수가 너무 적으면 MQA에 가까워지고, 너무 많으면 MHA에 가까워져 cache 절감 효과가 줄어든다.

셋째, 기존 MHA 모델을 GQA로 바꾸려면 단순 설정 변경만으로 끝나지 않을 수 있다. 논문은 K/V projection을 mean pooling으로 변환한 뒤 uptraining을 수행했다.

넷째, inference engine과 모델 구현이 GQA를 제대로 지원해야 실제 이득을 볼 수 있다. KV head 수가 줄어도 runtime이 이를 효율적으로 사용하지 못하면 기대한 decoding speed 개선이 나오지 않을 수 있다.

다섯째, 논문 자체도 평가 한계를 언급한다. 긴 sequence generation에서 memory bandwidth overhead가 중요하지만, 긴 생성 품질을 평가하는 것은 어렵다. 또한 논문은 XXL GQA 모델을 처음부터 학습한 모델과 직접 비교하지 않았고, 주 실험은 encoder-decoder 모델에 한정되어 있다.

## 12. 내가 이해한 핵심

GQA를 처음 보면 MHA와 MQA 사이에 head 수만 하나 더 추가한 구조처럼 보인다. 하지만 내가 이해한 핵심은 **quality와 memory cost를 조절할 수 있는 축을 만든 것**이다.

```text
MHA: query head마다 K/V를 따로 저장한다.
MQA: 모든 query head가 하나의 K/V를 공유한다.
GQA: query head를 group으로 묶고 group마다 K/V를 공유한다.
```

LLM inference에서 긴 context와 긴 output은 KV cache를 크게 만든다. 특히 decode 단계에서는 매 step마다 이전 token들의 K/V를 읽어야 하므로 memory bandwidth가 병목이 되기 쉽다. GQA는 이때 KV head 수를 줄여 cache와 bandwidth 부담을 줄인다.

한 문장으로 정리하면 다음과 같다.

```text
GQA는 여러 Query head를 그룹으로 묶고, 각 그룹이 하나의 Key/Value head를 공유하게 해서 KV cache를 줄이는 attention 구조다. MQA보다 품질 손실이 적고, MHA보다 추론 메모리와 대역폭 비용이 낮다.
```
