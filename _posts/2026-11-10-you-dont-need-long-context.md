에이전트가 오래 일할수록 대화 기록은 길어진다. 긴 문서를 한 번에 읽히면 입력 컨텍스트도 커진다. 그렇다면 긴 작업을 하려면 모델이 매번 긴 컨텍스트를 받아야 할까?

논문 [*You don’t need long context*](https://arxiv.org/abs/2611.05306)은 이 질문을 두 종류의 작업으로 나눠 실험한다. 여러 차례 행동하며 기록이 쌓이는 **long-horizon 작업**, 그리고 원본 자료 자체가 긴 **long-input 작업**이다. 저자들은 기록 압축과 선택적 읽기를 적용해도 여러 벤치마크의 정확도가 대체로 유지되며, 한 행동마다 대화를 새로 시작하는 설정도 가능하다고 보고한다.

다만 결론은 “어떤 작업에도 긴 컨텍스트가 쓸모없다”가 아니다. 연구가 보여주는 것은 **긴 기록이나 긴 입력을 매 추론 단계마다 전부 활성 컨텍스트에 넣어둘 필요는 없을 수 있다**는 점이다.

## 왜 긴 컨텍스트를 줄이려 하나

컨텍스트가 길어지면 입력 처리뿐 아니라 뒤이어 생성하는 토큰의 비용과 지연도 커질 수 있다. 저자들의 서빙 측정에서는 256K 컨텍스트 대신 16K로 운영할 때 출력 토큰 처리량이 GLM 5.2에서 3.6배, Kimi K2.6에서 5.6배, Qwen 3 Coder Next에서 7배 높았다. 로컬 모델 측정에서도 입력이 길어질수록 토큰 간 지연과 메모리 사용량이 증가했다.

이 동기는 API 사용자가 보는 토큰 단가와 구분해야 한다. 논문에서 비용 절감 배수를 계산할 때는 GPU 처리량과 서빙 비용을 바탕으로 추정한 운영 비용을 썼다. 따라서 그 배수가 모든 API 가격표나 실제 서비스의 청구액에 그대로 적용된다는 뜻은 아니다.

## 세 가지 연구 질문

논문은 긴 컨텍스트가 생기는 주요 원인을 두 가지로 본다.

1. **Long-horizon 작업(LCW1)**: 코드를 탐색하고 수정하거나 도구를 여러 번 호출하는 등, 이전 행동과 관찰에 의존해 작업이 이어진다. 행동과 도구 결과를 계속 대화에 붙이면 기록이 길어진다.
2. **Long-input 작업(LCW2)**: 긴 보고서, 논문, 여러 문서처럼 다뤄야 할 원자료가 크다. 모든 내용을 처음부터 컨텍스트에 넣으면 입력이 길어진다.

이를 다음 질문으로 구체화한다.

- **RQ1**: 긴 작업 기록을 매번 유지하지 않아도 long-horizon 작업을 끝낼 수 있을까?
- **RQ2**: 원자료 전체를 한 번에 넣지 않고도 long-input 작업을 해결할 수 있을까?
- **RQ3**: 추론 컨텍스트마다 행동을 하나만 수행해도 long-horizon 작업을 완료할 수 있을까?

논문에서 말하는 context는 모델이 한 번 추론할 때 제공받는 전체 토큰열이다. 시스템 지시, 작업 입력, 과거 답변, 도구 결과 등이 들어갈 수 있다. 이 연구의 대략적인 기준으로 256K 토큰 안팎은 긴 컨텍스트, 16K~50K는 짧은 컨텍스트다. ‘짧다’고 해도 절대적인 의미에서 작은 양은 아니다.

## 실험 방식: 기록을 얼마나 남길까

저자들은 같은 기본 에이전트 루프에 세 가지 기록 관리 방식을 적용했다.

![전체 기록 누적(FHA), 임계치 압축(EoCC), 행동마다 압축(SAC)의 차이]({{ '/assets/images/blog/long-context-regimes.png' | relative_url }})

1. **FHA(Full-History Accumulation)**: 작업이 끝날 때까지 모든 모델 행동과 환경 관찰을 한 대화에 계속 누적한다. 대화 기록을 지우거나 요약하지 않는 기준선이다.
2. **EoCC(End-of-Conversation Compaction)**: 컨텍스트가 정해둔 임계치에 닿으면 모델이 현재까지의 상태를 압축한다. 새 대화에 원래 작업 지시와 압축 상태를 넣고 작업을 이어간다. 필요하면 이 과정을 반복한다.
3. **SAC(Single-Action Compaction)**: 한 대화에서 환경 행동을 딱 하나 수행하고 결과를 관찰한 뒤, 의미 상태를 갱신한다. 그 대화를 버리고 갱신된 상태로 다음 추론을 시작한다.

컨텍스트 길이는 **최대(peak)**와 **총합(total)**을 나눠 봐야 한다. 한 번의 추론이 얼마나 긴 컨텍스트를 처리하는지가 최대 길이다. 압축을 거친 실행의 총 길이는 그 실행 중 만들어진 여러 대화 길이를 합산한다. 최대 컨텍스트가 짧아졌다고 해서 전체 토큰 사용량도 같은 비율로 줄었다고 단정할 수는 없다.

긴 입력 실험에서는 입력 문서를 `input01.txt` 같은 파일로 환경에 두었다. 모델은 `head`, `sed` 등의 도구로 필요한 부분을 선택해 읽는다. 즉 원문 전체를 매번 컨텍스트로 전달하는 대신, 파일을 필요할 때 찾아보도록 했다.

## RQ1: 긴 작업 기록을 압축해도 될까?

저자들은 SWE-bench Verified, Terminal-Bench, SWE-bench Multilingual, FRAMES, BFCLv3, Tau2Bench 등 여섯 long-horizon 벤치마크에서 압축 임계치를 낮춰가며 비교했다. 모델은 Claude Opus 4.5와 GPT 5.6 Sol이다.

![컨텍스트 제한을 낮춘 EoCC 설정에서의 정확도 변화와 비용 절감 추정]({{ '/assets/images/blog/long-horizon-compaction-results.png' | relative_url }})

기준선 대비 정확도 변화 범위는 Claude Opus 4.5가 **-3.7~+5.6%p**, GPT 5.6 Sol이 **-3.3~+4.4%p**였다. 범위의 양끝만 보면 변동이 커 보일 수 있지만, 두 모델 모두 22개 임계치 설정 중 기준선보다 2%p 넘게 하락한 경우는 5개 이하였다. 저자들이 추정한 비용 절감 배수는 Opus 4.5에서 **2.2~8.8배**, GPT 5.6 Sol에서 **2.4~5.0배**였다.

여기서 중요한 건 기록 자체를 없애자는 주장이 아니라는 점이다. 예를 들어 동전을 100번 던진 뒤 38번째 결과를 물어본다고 하자. 요약 과정에서 개별 결과가 사라졌다면 답하기 어렵다. 논문은 이런 경우 전체 기록을 모델의 매 추론 컨텍스트에 계속 넣는 대신, 기록을 외부에 보존하고 필요한 순간 선택적으로 조회하면 된다고 설명한다. 저자들의 주장은 “대화 기록을 조회할 필요가 없다”가 아니라 “전체 기록을 항상 컨텍스트 안에 둘 필요는 없다”에 가깝다.

## RQ2: 긴 문서를 선택적으로 읽어도 될까?

LongBench v2, LOONG, AA-LCR, NIAH, RULER, Counting-Stars, BABILong 등 일곱 long-input 벤치마크에서 전체 문서를 받은 기준선과 파일에서 필요한 부분을 찾아 읽는 방식을 비교했다.

![선택적 읽기를 적용한 long-input 벤치마크의 정확도 변화와 비용 절감 추정]({{ '/assets/images/blog/long-input-selective-reading-results.png' | relative_url }})

논문이 보고한 기준선 대비 정확도 변화는 Opus 4.5에서 **-0.4~+40.0%p**, GPT 5.6 Sol에서 **+1.0~+30.9%p**다. 비용 절감 추정 범위는 각각 **6.5~54.6배**, **4.4~233.3배**다. 성능 향상 폭과 비용 절감 폭이 큰 일부 결과는 모든 문서형 작업에서 그대로 기대할 수 있는 값이라기보다, 특정 벤치마크와 설정에서 관찰된 결과로 보는 편이 정확하다.

이 실험의 실용적인 아이디어는 단순하다. 긴 원문은 파일이나 검색 가능한 저장소에 두고, 질문에 필요한 부분만 찾아 모델에게 보여준다. 문서 길이가 커져도 모델이 읽고 추론하는 양이 그 길이에 비례해 계속 커질 필요는 없다는 것이다. 다만 모델이 필요한 근거를 찾아내는 능력과 파일 탐색 도구의 품질이 결과에 영향을 준다.

## RQ3: 행동 하나마다 대화를 새로 시작할 수 있을까?

SAC 실험은 SWE-bench Verified와 Terminal-Bench 2.1에서 진행했다. 모델은 매 대화에서 한 번의 환경 행동만 수행하고, 결과를 짧은 의미 상태에 반영한 뒤 다음 대화로 넘어간다.

Claude Opus 4.5의 정확도는 SWE-bench Verified에서 기준선 **70.0%**와 비슷한 **70.2%**, Terminal-Bench에서 **47.2%**에서 **51.8%**로 올랐다. GPT 5.6 Sol은 각각 **84.4% → 82.4%**, **87.6% → 84.3%**로 낮아졌다. 따라서 SAC가 모든 모델에서 정확도를 보존한 것은 아니다. 다만 감소 폭은 2.0~3.3%p였다. 중앙값 기준 최대 활성 컨텍스트는 **7~9K 토큰**이었고, 실험에서 관찰한 최대치는 기준선의 130~200K에서 SAC의 15~37K로 내려갔다.

이 결과에서 저자들은 **SSSM(Semantic State Space Model)**이라는 아이디어를 제안한다. 대화 전체를 매번 다시 읽는 대신, 자연어로 표현된 현재 의미 상태를 입력받아 다음 행동을 추론하고, 행동 결과를 기록해 상태를 갱신하는 모델이다. 이는 실험을 통해 이미 구현되고 검증된 별도 모델이라기보다, SAC 결과를 바탕으로 제안한 학습 방향이다. 기존 State Space Model의 신경망 내부 상태와 달리, SSSM은 대화 사이에 설명 가능한 언어 상태를 유지한다.

## 결과를 어디까지 받아들여야 할까

이 논문의 설득력은 서로 다른 상황을 나눠 확인했다는 데 있다. 작업 중 쌓이는 기록은 압축하고, 긴 원문은 선택적으로 읽고, 더 나아가 행동마다 컨텍스트를 새로 만드는 방식까지 실험했다. 단일한 긴 컨텍스트 기준선보다 늘 뛰어나다고 주장하기보다, 짧게 유지해도 많은 평가에서 성능이 크게 무너지지 않았다는 관찰을 제시한다.

반면 결과의 적용 범위는 실험한 모델·하네스·벤치마크에 묶여 있다. 압축은 손실이 있는 요약이므로, 나중에 특정 원문 기록을 정확히 다시 물어보는 작업에는 외부 기록과 검색이 필요할 수 있다. 긴 입력도 선택적으로 읽는 과정에서 필요한 근거를 놓칠 수 있다. 또한 비용 절감 수치는 실제 API 청구 금액을 그대로 예측하는 지표가 아니며, 짧은 컨텍스트가 정확도를 항상 높인다는 의미도 아니다.

그래서 실무적인 결론은 **컨텍스트를 줄이되, 원본과 상태를 다시 찾아볼 수 있게 설계하자**에 가깝다. 작업 상태에는 다음 행동에 필요한 목표, 결정, 진행 결과를 남기고, 정확한 과거 사실이나 긴 자료는 파일·로그·검색 인덱스에 보존해 필요할 때 읽는다. 이 분리는 토큰 비용뿐 아니라 모델이 현재 작업에 집중하는 데에도 도움이 될 수 있다.
