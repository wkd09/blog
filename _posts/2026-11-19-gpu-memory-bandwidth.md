지난 글의 마지막에 이런 질문이 남았다. GPU에 연산 장치가 수천 개 있어도 데이터를 제때 가져오지 못하면 기다려야 한다. 그러면 코어를 두 배로 늘려도 실행 시간이 그대로인 작업이 있을까? [이전 글 · 01 GPU architecture]({{ site.baseurl }}{% post_url 2026-11-18-gpu-architecture-parallelism %})

큰 배열 두 개를 원소별로 더하는 `C[i] = A[i] + B[i]`를 생각해 보자. 각 원소가 4바이트짜리 실수(FP32)라면, 덧셈 한 번에 입력 8바이트를 읽고 결과 4바이트를 쓴다. 배열이 캐시보다 크고 각 원소가 GPU 메모리를 한 번씩 오간다고 가정하면, **덧셈 하나를 끝내는 데 12바이트를 옮겨야 한다.** 이미 메모리 통로가 꽉 찼다면 코어를 두 배로 늘려도 그 12바이트가 더 빨리 도착하지는 않는다.

## 통로를 넓히면 무엇이 빨라질까?

GPU 메모리에 데이터를 요청하고 그 값을 쓸 수 있을 때까지 걸리는 시간이 **지연 시간(latency)**이다. 여러 요청을 연달아 보낼 때 1초 동안 옮길 수 있는 데이터의 양은 **대역폭(bandwidth)**이다. 첫 물방울이 호스 끝에 도착할 때까지 초시계를 보면 지연 시간을 잰다. 물이 흐르기 시작한 뒤 1초 동안 양동이에 몇 리터가 차는지 보면 대역폭을 잰다.

수천 개의 스레드가 한꺼번에 데이터를 요구하면 두 번째 숫자가 중요해진다. GPU가 계산할 수 있는 속도를 메모리에서 데이터를 공급하는 속도가 따라가지 못하는 문제를 **메모리 벽(memory wall)**이라고 한다.

![기판 배선으로 GPU와 연결되는 GDDR과 GPU 옆에서 넓은 인터페이스로 연결되는 적층 HBM]({{ '/assets/images/blog/gpu-gddr-hbm.png' | relative_url }})

그림 왼쪽의 GDDR은 그래픽 카드 기판 위에 놓인 메모리 칩과 GPU가 고속 신호를 주고받는 방식이다. 오른쪽의 HBM은 메모리 칩을 층층이 쌓고 GPU 가까이에서 아주 넓은 인터페이스로 연결한다. 정원용 호스를 소방용 호스로 바꾸면 같은 시간에 물을 더 많이 보낼 수 있듯, HBM은 많은 비트를 동시에 옮겨 높은 대역폭을 낸다. 그래도 다음 계산이 특정 값 하나에 달려 있다면 그 값이 도착할 때까지 기다려야 한다. [Micron의 HBM 구조 설명](https://www.micron.com/products/memory/hbm)

## 다른 일을 하는 게 왜 ‘지연 숨기기’일까?

처음엔 이 표현이 좀 이상했다. 데이터를 기다리는 동안 다른 일을 한다면 그냥 계속 일하는 것 아닌가? 맞다. 여기서 **누가 기다리고 있는지**를 나눠 보면 이름이 이해된다.

NVIDIA GPU에서는 스레드 32개가 한 **워프(warp)**로 묶인다. 워프 A가 메모리에 값을 요청했고, 다음 명령은 그 값을 더하는 일이라고 하자. A는 잠시 멈춘다. 그동안 SM(워프들이 실행되는 연산 장치 묶음)의 스케줄러는 이미 SM에 올라와 있는 워프 B에서 실행할 준비가 된 명령을 골라 보낸다. 나중에 A의 값이 도착하면 A의 덧셈도 실행할 수 있다.

A가 값을 받기까지 걸린 시간은 그대로다. 다만 그사이에 B의 계산이 끝났으니, A의 대기 시간만큼 GPU 전체가 쉬지는 않았다. 이렇게 **대기와 다른 계산을 겹치는 것**이 지연 숨기기다. 밖에서 새 작업이 계속 들어올 필요도 없다. 이미 올라와 있는 워프에 독립적으로 실행할 명령이 있으면 된다. 반대로 모든 워프가 데이터를 기다린다면 스케줄러도 그 시간을 숨길 수 없다. [CUDA Programming Guide의 하드웨어 멀티스레딩 설명](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-c-programming-guide/index.html#hardware-multithreading)

## FLOPS와 대역폭 중 어느 쪽을 봐야 할까?

**FLOPS**는 1초에 수행하는 부동소수점 연산 횟수이고, 메모리 대역폭은 보통 GB/s나 TB/s로 표시한다. 내 코드가 어느 쪽에 먼저 막히는지 알려면 두 숫자를 이어 줄 값이 하나 더 필요하다. 바로 **연산 강도(arithmetic intensity)**다. 여기서는 GPU의 외부 메모리에서 읽고 쓴 바이트당 몇 번의 부동소수점 연산을 했는지 센다.

![가로축은 바이트당 연산 수, 세로축은 초당 연산 수이며 대역폭에 따른 경사면이 연산 성능의 수평 지붕과 만나는 Roofline 그래프]({{ '/assets/images/blog/gpu-bandwidth-roofline.png' | relative_url }})

이 **Roofline 그래프**의 가로축은 연산 강도(FLOP/바이트), 세로축은 연산 처리량(FLOP/s)이다. 선은 그 GPU에서 기대할 수 있는 이론적 상한을 그린다. 그림을 읽기 위해 FP32 최고 처리량이 **12 TFLOP/s**, 메모리 대역폭이 **1.2 TB/s**인 GPU를 가정해 보자.

**왼쪽 경사면.** 앞의 벡터 덧셈은 12바이트를 옮겨 덧셈을 한 번 하므로 연산 강도가 1/12 FLOP/바이트다. 대역폭을 전부 써도 초당 가능한 덧셈은 1.2조 바이트 ÷ 12바이트, 즉 **1,000억 번(0.1 TFLOP/s)**이다. 사양표에는 12 TFLOP/s라고 쓰여 있지만, 이 작업에서는 메모리가 벌써 바쁘다. 이때는 대역폭을 높이거나 옮기는 바이트 수를 줄여야 속도가 오른다.

**오른쪽의 평평한 지붕.** 같은 GPU에서 1바이트를 옮길 때 평균 10번 연산하면 1.2 TB/s × 10 FLOP/바이트 = 12 TFLOP/s가 된다. 여기가 지붕이 꺾이는 점이다. 이보다 더 많이 재사용하는 코드라면 메모리가 충분히 공급해도 연산 장치가 먼저 한계에 닿을 수 있다. 큰 행렬 곱에서 입력값 하나를 여러 출력 계산에 돌려 쓰는 경우가 그렇다.

결국 GPU를 고를 때는 자주 돌릴 작업이 그래프 어디쯤에 놓이는지부터 보면 된다. 큰 배열을 한 번 훑는 작업이라면 메모리 대역폭을, 같은 데이터를 여러 번 곱하고 더한다면 해당 자료형의 연산 처리량을 먼저 본다. 실제 측정값은 지붕 아래에 놓일 수 있다. 가령 동시에 실행할 워프가 너무 적으면 메모리와 연산 장치 양쪽에 여유가 있어도 느리다. [NVIDIA의 GPU 성능 가이드](https://docs.nvidia.com/deeplearning/performance/dl-performance-gpu-background/#understanding-performance)

## 은행 창구에서 보는 GPU 메모리 계층

그럼 같은 GPU에서 코드를 바꿔 경사면을 올라갈 방법도 있을까? 은행원이 손님에게 만 원권을 열 장씩 건네는 상황을 떠올려 보자. 지하 금고에 지폐가 아무리 많아도 손님 한 명이 올 때마다 지하에 다녀오면 줄이 길어진다. 한 번 다녀올 때 여러 묶음을 가져와 창구 가까이에 두면 같은 손님들을 훨씬 빨리 처리할 수 있다.

![레지스터에서 L1 캐시와 공유 메모리, L2 캐시, 글로벌 메모리로 내려갈수록 접근 지연과 저장 용량이 대체로 늘어나는 계단 그림]({{ '/assets/images/blog/gpu-memory-hierarchy.png' | relative_url }})

| 은행 창구에서 | GPU에서 | 어떤 값을 두는가 |
|---|---|---|
| 손에 들고 세는 지폐 | 레지스터 | 스레드 하나가 지금 계산 중인 값. 행렬 곱에서 곱셈 결과를 차곡차곡 더하는 누산값이 한 예다. |
| 창구 바로 옆 서랍 | L1 캐시 | SM 가까이에서 최근 접근한 데이터를 다시 꺼내 쓴다. 어떤 데이터를 남길지는 하드웨어가 관리한다. |
| 같은 창구 직원들이 쓰는 트레이 | 공유 메모리 | 한 스레드 블록이 함께 쓸 데이터를 프로그래머가 명시적으로 올려 둔다. |
| 여러 창구가 함께 쓰는 지점 금고 | L2 캐시 | 여러 SM이 공유한다. L1에서 찾지 못한 값도 L2에 있으면 외부 메모리까지 갈 필요가 없다. |
| 지하 금고 | 글로벌 메모리를 뒷받침하는 VRAM | 큰 배열과 모델 가중치가 있는 곳이다. 온칩 캐시에서도 찾지 못하면 여기까지 다녀온다. |

그림에서 L1 캐시와 공유 메모리가 같은 계단에 있는 데 주목하자. L1은 하드웨어가 채워 주는 서랍이고, 공유 메모리는 블록의 스레드들이 용도를 정해 쓰는 트레이다. CUDA에서는 `__shared__`로 공간을 선언한 뒤 스레드들이 필요한 값을 직접 채워 넣는다. 일반 변수는 컴파일러가 레지스터에 둘 수 있지만, 레지스터가 부족하면 일부 값은 다른 메모리로 밀려날 수 있다. [CUDA C++ Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/#memory-optimizations)

행렬 곱에서는 같은 행의 여러 출력값을 구할 때 입력 행렬 A의 같은 원소를 곱셈에 여러 번 쓴다. 이때 한 블록이 쓸 입력 조각, 즉 **타일(tile)**을 공유 메모리에 함께 읽어 두고, 준비가 끝나면 각 스레드가 그 조각에서 값을 꺼내 자기 출력값에 곱해 더한다. 필요한 곱셈 횟수는 그대로인데 외부 메모리와 오가는 바이트가 줄어든다. 앞의 Roofline 그래프에서 오른쪽으로 이동한다는 게 바로 이런 뜻이다.

이 관점은 평소 쓰는 프로그램에도 적용된다. 언어 모델이 토큰을 하나 생성할 때와 여러 요청의 토큰을 묶어서 생성할 때를 생각해 보자. 묶어서 처리하면 한 번 읽은 가중치로 여러 입력을 계산할 수 있어 바이트당 연산 수가 늘어난다. 게임에서 이웃 픽셀들이 같은 텍스처 영역을 읽거나, 영상 필터가 이웃 픽셀을 여러 번 참조할 때도 가까운 곳에 남아 있는 값을 쓸 기회가 생긴다.

처음의 벡터 덧셈으로 돌아가 보자. 두 배열을 더하고 결과를 한 번 쓰면 끝이라 그 12바이트 안에서는 재사용할 여지가 거의 없다. 그런데 바로 다음 단계에서 모든 결과에 2를 곱한다면 어떨까? 두 단계를 따로 실행하면 중간 배열을 쓰고 다시 읽어야 한다. 한 번에 `C[i] = 2 * (A[i] + B[i])`를 계산하면 중간값을 레지스터에 둔 채 최종 결과만 쓸 수 있다. 내 코드가 메모리를 기다린다면, 가장 먼저 찾아볼 곳은 이렇게 **방금 쓴 값을 곧바로 다시 읽는 줄**이다.
