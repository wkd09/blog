그래픽 렌더링을 위해 발전한 GPU는 이제 AI 모델의 학습과 추론에도 사용된다. GPU가 이런 작업에 강한 이유는 무엇일까? 핵심은 코어 숫자보다 **작업을 어떻게 나누고, 데이터를 얼마나 빠르게 공급할 수 있는지**에 있다.

## CPU와 GPU는 무엇이 다를까?

CPU는 **Central Processing Unit**, GPU는 **Graphics Processing Unit**이다. 둘 다 프로그램의 명령을 실행하고 데이터를 처리하지만, 하드웨어 자원을 사용하는 데 서로 다른 우선순위를 둔다.

| | CPU | GPU |
|---|---|---|
| 주요 목표 | 다양한 작업의 빠른 응답과 유연한 실행 | 많은 데이터에 대한 높은 처리량 |
| 실행 구조 | 비교적 복잡하고 강력한 소수의 코어 | 다수의 연산 장치를 묶어 대량의 스레드 실행 |
| 적합한 작업 | 운영체제, 분기와 상호작용이 많은 프로그램 | 행렬 연산, 그래픽, 데이터 병렬 계산 |

이 구분은 경향을 설명한 것이다. CPU도 여러 코어와 SIMD 명령으로 병렬 계산을 수행하고, GPU도 분기와 순차적인 명령을 실행할 수 있다. 같은 프로그램이라도 데이터 크기와 구현 방법에 따라 더 적합한 장치가 달라진다.

여기서 자주 비교하는 두 지표가 있다.

- **지연 시간(latency)**: 하나의 작업이 시작해 끝날 때까지 걸리는 시간
- **처리량(throughput)**: 일정 시간 동안 완료한 작업의 양

GPU는 많은 작업을 진행해 높은 처리량을 얻는 데 강하지만, 그렇다고 모든 단일 작업의 지연 시간이 더 짧아지는 것은 아니다.

## GPU가 빠르다면 운영체제도 GPU에서 실행하면 되지 않을까?

운영체제는 사용자 입력과 하드웨어 이벤트에 반응하고 수시로 실행 경로를 바꾸므로, 복잡한 제어와 짧은 응답 시간이 중요하다. GPU도 분기와 인터럽트를 처리할 수 있지만, 비슷한 연산을 많은 데이터에 적용할 때 자원을 더 효율적으로 사용한다. 보통 CPU가 운영체제와 프로그램의 흐름을 관리하고, GPU가 병렬성이 큰 작업을 가속한다.

## 행렬 곱은 왜 GPU에 잘 맞을까?

두 $3 \times 3$ 행렬 $A$와 $B$를 곱해 $C = AB$를 구한다고 하자. 결과 행렬 $C$에는 아홉 개의 원소가 있다.

$$
C_{ij} = \sum_{k=0}^{2} A_{ik}B_{kj}
$$

각 출력 원소 $C_{ij}$는 **$A$의 $i$번째 행과 $B$의 $j$번째 열**을 사용해 계산한다. 입력 행렬이 준비되어 있다면, $C_{0,0}$을 구한 결과가 $C_{2,2}$를 구하기 위한 입력이 되지는 않는다. 따라서 서로 다른 출력 원소의 계산을 나눠 진행할 수 있다.

![3×3 행렬 곱에서 출력 원소를 나누어 계산하는 개념도]({{ '/assets/images/blog/gpu-matrix-parallelism.png' | relative_url }})

*출력 원소 사이의 독립성을 보여주는 개념도다. 그림 아래 설명과 달리 $C_{ij}$는 $A$의 $i$번째 행과 $B$의 $j$번째 열에 의존한다. 또한 그림의 코어와 스레드 대응은 이해를 위한 단순화이며 실제 구현이 물리 코어 하나에 출력 하나를 고정한다는 뜻은 아니다.*

예를 들어 $10{,}000 \times 10{,}000$ 행렬 두 개를 곱하면 결과에 **1억 개의 원소**가 생긴다. 각 원소는 길이 10,000인 두 벡터의 곱과 합으로 계산하므로, 단순한 곱셈·덧셈을 각각 한 번의 부동소수점 연산으로 세면 전체 연산량은 약 $2 \times 10^{12}$ FLOPs다.

GPU가 1억 개의 물리 코어를 동시에 사용하는 것은 아니다. 논리적 작업을 제한된 실행 장치에서 여러 차례에 걸쳐 처리한다. CPU도 여러 코어와 벡터 명령으로 행렬 곱을 병렬화할 수 있지만, 충분히 큰 행렬에서는 GPU의 높은 처리량이 유리한 경우가 많다.

GEMM(General Matrix Multiplication)은 $C = \alpha AB + \beta C$ 형태의 연산이다. 고성능 구현은 입력을 **타일(tile)**로 나눠 재사용하고, 지원되는 데이터 타입과 하드웨어에서는 **Tensor Core**도 활용한다.

## CPU 코어와 GPU의 SM

연산 장치를 이해하기 위해 ALU와 제어 장치를 구분해 보자.

- **ALU(Arithmetic Logic Unit)**는 덧셈, 비교 같은 산술·논리 연산을 수행한다.
- **제어 장치**는 명령을 해석하고 어떤 연산을 수행할지 실행 흐름을 제어한다.

CPU 코어는 복잡한 분기와 데이터 의존성을 빠르게 처리하는 데 집중하고, GPU는 비슷한 연산을 많은 데이터에 적용할 수 있도록 다수의 연산 장치를 구성한다.

![CPU 코어와 GPU SM의 제어·캐시·연산 자원을 비교한 개념도]({{ '/assets/images/blog/gpu-cpu-sm-control.png' | relative_url }})

*CPU와 GPU의 자원 구성에 대한 직관을 보여주는 그림이다. 실제 CPU 코어와 GPU의 SM은 그림보다 복잡하다. 하나의 관리자가 GPU 전체의 수천 개 코어를 동시에 제어하는 구조로 이해하면 안 된다.*

NVIDIA GPU에는 여러 **SM(Streaming Multiprocessor)**이 있다. 각 SM에는 명령을 스케줄링하는 하드웨어, 여러 종류의 연산 장치, 레지스터와 공유 메모리 등의 자원이 들어 있다. **CUDA Core**는 SM 안의 연산 장치에 붙는 NVIDIA의 명칭이다.

CPU 코어, CUDA Core, Tensor Core, 소프트웨어 스레드는 서로 다른 개념이다. CUDA Core 하나가 스레드 하나를 처음부터 끝까지 전담하는 것도 아니다.

## CUDA의 thread, block, warp는 어떻게 실행될까?

CUDA는 NVIDIA GPU에서 병렬 프로그램을 작성하고 실행하기 위한 플랫폼과 프로그래밍 모델이다. GPU에서 실행할 함수를 **kernel**이라고 부른다.

프로그래머는 kernel을 실행할 때 작업을 스레드와 블록으로 구성한다.

    Grid
    ├── Block 0
    │   ├── Thread 0, Thread 1, ...
    │   └── Thread ...
    ├── Block 1
    │   └── Thread ...
    └── ...

- **Thread**: kernel 코드를 실행하는 논리적인 작업 단위. 스레드마다 인덱스와 작업할 데이터가 다를 수 있다.
- **Block**: 여러 스레드를 묶은 단위. 같은 블록의 스레드는 공유 메모리를 이용하고 정해진 방식으로 동기화할 수 있다.
- **Grid**: 한 번의 kernel 실행에 포함된 블록들의 집합.
- **SM**: 실행할 블록을 배정받아 스레드들을 처리하는 GPU의 하드웨어 단위.

NVIDIA의 CUDA 실행 모델에서는 SM이 블록의 스레드들을 **32개 스레드로 이루어진 warp**로 나누어 스케줄링한다. 이를 **SIMT(Single Instruction, Multiple Threads)** 실행 모델이라고 한다. 같은 warp의 스레드는 같은 명령을 각자의 데이터에 적용할 수 있지만, 스레드마다 인덱스와 상태를 갖는다. 하나의 SM에서 여러 warp가 실행 준비 상태로 존재할 수 있으며, 어떤 warp가 메모리 응답을 기다리는 동안 다른 준비된 warp를 실행해 지연을 숨길 수 있다.

### Warp divergence: 같은 warp에서 서로 다른 길을 가면

같은 warp의 스레드가 if/else에서 서로 다른 경로를 선택하면 **warp divergence**가 발생할 수 있다. 하드웨어가 실행하는 경로에 해당하지 않는 스레드의 lane은 그 경로에서 비활성화되므로 실행 효율이 떨어질 수 있다.

GPU 전체가 직렬로 실행되는 것은 아니며, 다른 warp는 독립적으로 스케줄링될 수 있다. 따라서 **같은 warp 안에서 작업이 얼마나 갈라지는지** 살펴보는 것이 중요하다.

## 병렬화가 가능하다는 것은 무슨 뜻일까?

코어가 많더라도 작업을 나눌 수 없다면 모든 코어를 유용하게 사용할 수 없다. 핵심은 각 작업이 **다른 작업의 결과를 얼마나 기다려야 하는가**, 즉 데이터 의존성이다.

- **행렬 곱**: 서로 다른 출력 원소를 병렬로 계산할 수 있다. 실제 구현에서는 입력을 공유하고 부분합을 합치는 과정에서 동기화가 필요할 수 있다.
- **정렬**: 여러 묶음을 동시에 정렬한 뒤 결과를 병합한다. 병합도 병렬화할 수 있지만 데이터 이동과 조정 비용이 든다.
- **연결 리스트 순회**: 현재 노드를 읽어야 다음 주소를 알 수 있으므로, 하나의 리스트를 앞에서부터 따라가는 경로에는 순차적 의존성이 있다.

이 한계는 특정 구현에 대한 것이다. 예를 들어 피보나치 수열을 앞에서부터 계산하는 방식에는 의존성이 있지만, 특정 항은 fast doubling처럼 다른 알고리즘으로도 구할 수 있다.

## 코어가 무한히 많아져도 빨라지지 않는 부분: Amdahl의 법칙

한 작업에서 병렬화할 수 없는 비율을 $s$, 나머지 부분을 $N$개의 처리 자원에 완벽하게 나눌 수 있다고 가정하면, 전체 속도 향상은 다음과 같다.

$$
S(N) = \frac{1}{s + \frac{1-s}{N}}
$$

예를 들어 전체 실행 시간의 30%가 직렬 구간이라면, 병렬 구간을 아무리 빠르게 처리해도 최대 속도 향상은 다음 값에 가까워진다.

$$
\lim_{N \to \infty} S(N) = \frac{1}{0.3} \approx 3.33
$$

이 계산은 **같은 크기의 작업**을 기준으로 하며, 병렬 부분이 완벽하게 나뉘고 추가 비용이 없다고 가정한다. 실제로는 작업 분배, 동기화, 데이터 전송과 메모리 경합 때문에 속도 향상이 더 작아질 수 있다. 반대로 알고리즘을 바꾸거나 작업의 크기를 늘리면 직렬 비율 자체가 달라질 수 있으므로, 위 숫자가 모든 상황의 고정된 한계는 아니다.

## 연산 장치가 많아도 데이터가 늦으면 기다려야 한다

GPU의 연산 장치가 빠르더라도 필요한 데이터를 제때 읽지 못하면 계산을 계속할 수 없다. 그래서 GPU 성능을 볼 때는 연산 성능과 함께 **메모리 대역폭(memory bandwidth)**을 봐야 한다.

대역폭은 일정 시간 동안 전송할 수 있는 데이터의 양이다. 예를 들어 NVIDIA A100의 공식 사양에서 GPU 메모리 대역폭은 40GB 모델이 **1,555 GB/s**, 80GB PCIe 모델이 **1,935 GB/s**, 80GB SXM 모델이 **2,039 GB/s**다. 이는 제품별 이론상 최대 대역폭이며 실제 프로그램에서 항상 이 속도가 나오는 것은 아니다.

A100은 HBM 계열 메모리를 사용하지만, 모든 GPU가 HBM을 사용하는 것은 아니다. GPU에 따라 GDDR을 사용하거나 시스템 메모리를 공유하기도 한다. CPU와 별도의 GPU가 있는 시스템에서는 CPU 메모리와 GPU 메모리 사이의 데이터 전송 비용도 고려해야 한다.

### GPU 메모리 계층

CUDA에서 자주 만나는 메모리 공간을 단순하게 정리하면 다음과 같다.

| 메모리 | 주로 접근하는 범위 | 용도와 특징 |
|---|---|---|
| Register | 개별 스레드 | 스레드의 임시 값 보관. SM의 제한된 자원을 사용 |
| Shared memory | 같은 블록의 스레드 | 스레드 간 데이터 공유와 타일 재사용 |
| Cache | 하드웨어가 관리 | 자주 쓰는 데이터에 대한 접근을 돕는 계층 |
| Global memory | GPU의 여러 스레드 | 큰 데이터를 보관하는 장치 메모리. 온칩 자원보다 접근 지연이 크다 |

메모리 공간과 물리적인 저장 위치가 항상 일대일로 대응하지는 않는다. 예를 들어 CUDA의 *local memory*는 이름과 달리 장치 메모리에 놓일 수 있다. 정확한 용량과 동작은 GPU 아키텍처에 따라 달라진다.

### 연산 강도와 타일링

**연산 강도(arithmetic intensity)**는 메모리에서 옮긴 데이터 양에 비해 얼마나 많은 연산을 수행하는지를 나타낸다.

$$
\text{Arithmetic intensity} = \frac{\text{수행한 연산 수}}{\text{전송한 데이터의 바이트 수}}
$$

같은 데이터를 한 번 읽고 한 번만 계산한다면 메모리 대역폭이 병목이 되기 쉽다. 반면 읽어 온 데이터를 여러 번 재사용하면 바이트당 연산 수가 늘어나 GPU의 연산 장치를 더 오래 활용할 수 있다.

행렬 곱의 타일링은 이 재사용을 위한 대표적인 방법이다. 입력 행렬의 일부를 가져와 여러 출력 계산에 함께 사용하면, 출력 원소마다 같은 값을 메모리에서 다시 읽는 단순한 방식보다 데이터 이동을 줄일 수 있다.

**Roofline 모델**은 이 관계를 이해하는 데 유용하다. 달성 가능한 연산 처리량을 단순화해 보면, 연산 강도와 메모리 대역폭의 곱으로 정해지는 경계와 연산 장치의 최고 처리량 중 낮은 쪽에 제한된다.

$$
\text{달성 가능한 처리량} \lesssim
\min(\text{최대 연산 처리량},\ \text{메모리 대역폭} \times \text{연산 강도})
$$

실제 성능에는 메모리 접근 패턴, 캐시, 데이터 타입, 스케줄링, kernel 실행 비용도 영향을 준다. Roofline은 정확한 실행 시간을 보장하는 공식이 아니라 **지금 무엇이 병목일 가능성이 큰지 생각하기 위한 모델**이다.

## 정리

GPU가 행렬 곱에 강한 이유는 독립적으로 나눌 수 있는 작업이 많고, 많은 연산 장치에 데이터를 공급하며 같은 입력을 재사용할 수 있기 때문이다. 이때 스레드가 늘어난다고 무조건 빨라지는 것은 아니다. 분기, 데이터 의존성, 동기화, 메모리 대역폭과 실행 비용이 모두 영향을 준다.

CPU는 복잡한 제어 흐름과 낮은 지연 시간이 필요한 작업을 처리하고, GPU는 충분한 병렬성이 있는 작업을 높은 처리량으로 가속한다. 중요한 것은 코어 숫자 하나가 아니라 **작업의 의존성, 데이터 이동, 연산량을 함께 보는 것**이다.
